# Названия прогонов PostgreSQL и добавление для сравнения — дизайн

## Цель

Исправить два связанных дефекта источников PostgreSQL:

1. Вместо пользовательского названия прогона интерфейс показывает технический источник `jsqdb://recording/<id>` или только ID.
2. Команда «Из БД…» заменяет текущую рабочую область выбранными прогонами, поэтому второй прогон нельзя добавить для сравнения с уже открытым источником.

Технический URI остаётся стабильным идентификатором источника. Пользовательское название хранится отдельно и применяется только для отображения.

## Подтверждённое поведение

- «Из БД…» добавляет выбранные записи к уже открытым источникам.
- Общий лимит рабочей области остаётся равным шести источникам независимо от их типа.
- Повторно выбранный источник не добавляется.
- При заполненной рабочей области приложение сообщает о лимите и ничего не очищает.
- Для прогона PostgreSQL отображается его поле `Название`; при пустом названии используется ID записи.
- Для папок и экспортированных протоколов сохраняется существующее отображение имени файла или папки.
- Дружественные имена применяются в заголовке графика, заголовках окон каналов и префиксах каналов при сравнении.
- Для нескольких источников заголовок графика перечисляет их имена через `;` в порядке workspace.
- Live-refresh по-прежнему поддерживается только для одиночного DB-источника. После успешного добавления второго источника таймер останавливается; неудачное добавление сохраняет прежний таймер через существующий rollback.

## Корневые причины

`MainForm.OpenFromDatabaseButtonOnClick` рассчитывает свободное количество источников с учётом текущего workspace, но после закрытия диалога создаёт новый список только из `SelectedSources`. Текущие источники отбрасываются.

Заголовки и подписи строятся непосредственно из `IViewerSession.Folder`, `TestData.Root` или `Path.GetFileName(sourceRoot)`. Для `jsqdb://recording/<id>` это технический URI/ID. Название уже читается из PostgreSQL в `TestData.Meta["Название"]`, но после объединения нескольких источников нет отдельной связи «источник → отображаемое имя».

## Модель данных

В `TestData` добавляется словарь:

```csharp
Dictionary<string, string> SourceDisplayNames
```

и упорядоченный список технических источников:

```csharp
string[] SourceOrder
```

Ключ — канонический source root (`jsqdb://recording/<id>`, путь к папке или `.xlsx`). Значение — дружественное имя.

Инварианты:

- словарь всегда не `null`;
- сравнение ключей регистронезависимое;
- `SourceOrder` всегда не `null`, не содержит повторов и задаёт порядок workspace независимо от порядка перечисления словарей на .NET Framework 4.8;
- для каждого источника в `SourceColumns` допускается отсутствие записи, но UI обязан использовать безопасный fallback;
- технические структуры `Root`, `SourceColumns`, `CodeSources`, `SourceStartMs` и `SourceEndMs` не заменяются дружественными именами.

## Формирование отображаемого имени

Единый resolver применяет правила в таком порядке:

1. Непустое значение `SourceDisplayNames[sourceRoot]` после `Trim()`.
2. Только для одиночного `jsqdb://recording/<id>` из старых/неполных данных — непустое `Meta["Название"]` после `Trim()`.
3. Для `jsqdb://recording/<id>` — ID записи.
4. Для файлового источника — существующий `Path.GetFileName` после удаления завершающих разделителей. Файловый `Meta["Название"]` не используется.
5. Исходная строка source root.

`PostgresRecordingDataSourceReader`/`RecordingRowsToTestDataMapper` записывает название из метаданных в `SourceDisplayNames`. `AppendNewWindows` сохраняет существующий словарь без изменения.

Файловые читатели не обязаны заполнять словарь: resolver сохраняет прежнее поведение через fallback.

Whitespace-only title считается отсутствующим. Одинаковые непустые названия разных PostgreSQL-прогонов разрешены. При построении набора подписей resolver обнаруживает коллизию без учёта регистра и выдаёт для каждого конфликтующего DB-источника `Название [полный recordingId]`. Неконфликтующие названия ID не содержат. Display name никогда не используется для дедупликации: два разных root сохраняют две записи `SourceDisplayNames`, две позиции в `SourceOrder`, два окна источников и два набора префиксов каналов. Поэтому технический root остаётся идентификатором, а пользователь видит ID только когда он действительно нужен для различения.

## Объединение и удаление источников

`MergeLoadedSourcesUseCase` объединяет `SourceDisplayNames` всех входных `TestData` по тем же каноническим root, которые используются в `SourceColumns`.

`SourceOrder` результата строится из входных `TestData` в порядке аргументов merge: сначала их `SourceOrder`, затем отсутствующие там root из `SourceColumns`. Повторы удаляются регистронезависимо с сохранением первого вхождения. Одиночная загрузка записывает единственный root; append копирует прежний порядок.

Если один canonical root встретился во входах с разными display names, побеждает первое непустое нормализованное значение. Это защитная политика: основной UI не должен передавать дублирующий root после дедупликации.

`RemoveLoadedSourceUseCase` создаёт новый регистронезависимый `SourceDisplayNames`, содержащий только root из оставшихся `SourceColumns`, и фильтрует `SourceOrder` в прежнем порядке. `AppendNewWindows` копирует/сохраняет оба поля и в ветке с новыми строками, и в ветке без них.

Все операции продолжают использовать source root как идентификатор; одинаковые названия разных прогонов допустимы и не приводят к конфликту.

## Добавление записей из БД

Объединение списков источников оформляется как тестируемая операция прикладного/оркестрационного слоя, а не как неявная манипуляция внутри event handler:

1. Разобрать текущий `FolderSpec`.
2. Добавить выбранные URI в порядке выбора.
3. Удалить дубликаты с `StringComparer.OrdinalIgnoreCase`, сохранив первое вхождение.
4. Проверить общий лимит `WorkspaceFolderSpecParser.MaxFolderCount`.
5. Если новых источников нет, показать сообщение о дубликате и не перезагружать workspace.
6. При успехе сформировать новый `FolderSpec` и вызвать существующий `LoadFolder`.

Лимит проверяется после дедупликации исключительно по техническому root. Если уникальных root получилось больше шести, вся операция отклоняется атомарно: показывается сообщение о лимите, `_folderBox` и workspace остаются неизменными, `LoadFolder` не вызывается. Выбор не урезается автоматически до доступного количества.

Если текущая рабочая область уже содержит шесть источников, диалог выбора не открывается и приложение показывает существующее сообщение о лимите. Текущий workspace никогда не очищается автоматически.

Смешанная рабочая область (папки, `.xlsx`, DB) обрабатывается теми же правилами. Если выбор частично пересекается с уже открытыми URI, добавляются только новые URI при условии, что итоговый список помещается в лимит. При полностью дублирующемся выборе или заполненном лимите `_folderBox` не меняется и `LoadFolder` не вызывается.

## Использование в UI

Один resolver дружественных имён и workspace-title builder используются в следующих местах:

- заголовок основного окна графика;
- заголовок отделённого графика;
- заголовки окон каналов;
- префиксы каналов/ролей прогноза при нескольких источниках;
- обновление подписей при смене языка.

Для одиночного источника заголовок графика содержит одно дружественное имя. Для нескольких — имена в `SourceOrder`, разделённые `; `. Источники не удаляются из заголовка только из-за совпадения названий: коллизии предварительно различаются через `[recordingId]`. Если определить ни одно имя нельзя, используется текущий `IViewerSession.Folder`.

`ChannelWorkspacePresenter.BindData` передаёт `SourceDisplayNames` и `SourceOrder` в `SourceWindowCoordinator`; coordinator формирует `SourceChannelWindowViewModel.Title` через resolver вместо прямого `Path.GetFileName`. `MainForm` не пересчитывает заголовки окон напрямую из root при `ApplyLocalization`, а повторно применяет уже разрешённые title к существующим source windows. Заголовки основного и отделённых графиков строятся одним workspace-title builder при bind, создании окна и смене языка. Префиксы каналов и роли прогноза используют тот же набор разрешённых подписей.

## Ошибки и совместимость

- Ошибка загрузки добавленного прогона обрабатывается существующим rollback в `LoadFolder`; прежняя рабочая область и live-refresh сохраняются.
- Отображаемое имя не участвует в запросах PostgreSQL, recent sources, workspace key и live-refresh.
- После успешного перехода от одного DB-источника к двум и более `UpdateLiveRefreshState` сохраняет текущее правило и выключает таймер. Multi-source live-refresh в эту доработку не входит.
- Старые `TestData`, тестовые fixtures и файловые источники совместимы благодаря инициализации словаря и fallback-правилам.
- JSON-форматы настроек и сохранённых layout не меняются.

## Тестирование

Автоматические регрессии должны подтвердить:

- текущие источники и выбранные записи БД объединяются в правильном порядке;
- дубликаты не добавляются;
- лимит шести источников не позволяет очистить или заменить workspace;
- mixed workspace сохраняется; при частичном пересечении добавляются только новые URI;
- при полностью дублирующемся выборе и заполненном лимите не изменяются `_folderBox` и вызовы загрузки;
- пять текущих источников плюс один уже открытый URI и один новый дают шесть источников: дубликат отбрасывается, новый добавляется;
- пять текущих источников плюс два новых отклоняются целиком без изменения workspace и без вызова загрузки;
- дедупликация выполняется только по техническому root, а не по display name;
- mapper создаёт имя записи из `Meta["Название"]`, обрезает пробелы и использует ID при пустом названии;
- файловый источник с собственным `Meta["Название"]` по-прежнему отображается по имени файла/папки;
- merge сохраняет отдельные имена двух записей;
- два разных DB URI с одинаковым `Название` сохраняют оба источника, обе записи `SourceDisplayNames`, обе позиции `SourceOrder` и обе UI-подписи с различающим ID; удаление одного выполняется по root и не затрагивает второй;
- merge использует первое непустое имя при повторном canonical root;
- remove удаляет только имя закрытого источника;
- append сохраняет имя и порядок активной записи в обеих ветках;
- `SourceOrder` сохраняется при single-load, merge, remove и append;
- resolver корректно обрабатывает DB, папки, несколько источников, одинаковые title и fallback;
- presenter-тесты подтверждают `SourceChannelWindowViewModel.Title`;
- тестируемый workspace-title builder и UI-вызовы используют resolver, а не технический URI;
- переход от одного к двум источникам останавливает live-refresh, а rollback неудачного добавления сохраняет его.

Ручная проверка:

1. Открыть запись из БД — заголовки графика и каналов содержат название, не ID.
2. Снова нажать «Из БД…», выбрать другую запись — обе записи остаются в workspace и доступны для сравнения.
3. Проверить одинаковые коды каналов: префиксы различают источники по названиям; для одинаковых названий добавляется `[recordingId]`.
4. Повторно выбрать уже открытую запись — дубликат не появляется.
5. Заполнить workspace до шести источников — следующий источник не добавляется, текущие данные остаются.
6. Для одиночной активной записи дождаться live-refresh — название и идентификатор источника не меняются. После добавления второго источника убедиться, что автообновление прекращено; после неудачного добавления оно продолжается.

## Не входит в изменение

- Изменение формата `jsqdb://recording/<id>`.
- Снятие лимита в шесть источников.
- Переименование записей в базе данных.
- Сохранение локальных пользовательских псевдонимов.
- Изменение SQL-каталога или алгоритма live-refresh, кроме передачи нового display-name поля через существующие данные.
