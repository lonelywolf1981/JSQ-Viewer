# Прогоны из PostgreSQL как источник данных JSQ Viewer

Дата: 2026-08-06

## Задача

JSQ Viewer читает данные испытаний из папок с DBF-файлами и из выгруженных
протоколов `.xlsx`. Параллельно работает сервис JSQ Laboratory, который пишет
измерения в PostgreSQL. Нужно дать Viewer возможность открывать прогоны прямо
из этой базы — как исторические, так и идущие в данный момент, — не теряя
существующую работу с файлами.

Подключение: `192.168.66.100:5432`, база `jsq_db`, пользователь `jsq_user`.

## Что уже есть в базе

PostgreSQL 15.17, схемы `public` и `auth`, 70 таблиц. Для задачи существенны:

| Таблица | Строк | Роль |
| --- | --- | --- |
| `recordings` | 190 | Прогон: пост, название, статус, начало/конец, полная карточка испытания (модель, хладагент, масса заправки, компрессор, конденсатор, тип испытания и т. д.) |
| `recording_aggregates` | 24 835 045 | Данные по каналам: `recording_id, channel_id, window_start, window_end, min/max/avg_value, sample_count` |
| `recording_computed_aggregates` | 3 207 543 | Расчётные каналы (`T-avg`, `T-min`, `T-max`, `T-cond`, `T-boil`) в том же формате |
| `recording_aggregate_exclusions` | 547 833 | Окна, исключённые оператором; активные — те, у которых `restored_at IS NULL` |
| `channel_config` | 149 | Алиас, единица, пороги, скрытость канала по постам |
| `channel_order` | 3 | Порядок каналов по постам (JSON-массив кодов) |
| `posts` | 3 | Посты `A`, `B`, `C` |

Каналы именуются с префиксом поста: `B-T1`, `C-Pe`, `A-MaxI`. Окно агрегации
хранится в `recordings.aggregation_window_seconds` (сейчас 20 с).

Замеры на самом длинном прогоне (125 ч, 40 каналов): 1 797 960 строк агрегатов,
из них 426 382 окна исключены. Полная выборка с отсечением исключений —
1 371 578 строк за 5.97 с по сети. Анти-джойн по исключениям практически
бесплатен благодаря частичному индексу `uq_active_exclusion
(recording_id, channel_id, window_start) WHERE restored_at IS NULL`.

## Принятые решения

1. Поддерживаются оба режима: открытие исторических прогонов и наблюдение за
   идущим. Работа с папками и `.xlsx` сохраняется без изменений.
2. Значение канала — `avg_value` окна агрегации.
3. Префикс поста в кодах каналов срезается: `B-T1` → `T1`.
4. Прогон выбирается в диалоге со списком и фильтрами.
5. Параметры подключения хранятся в настройках приложения с предзаполненными
   значениями по умолчанию.
6. Активный прогон дозагружается автоматически по таймеру.
7. Окна, исключённые оператором, не показываются — картинка совпадает с
   веб-сервисом.
8. Расчётные каналы из `recording_computed_aggregates` не загружаются.

## Архитектура

Прогон из БД становится третьим типом источника наравне с папкой DBF и
выгруженным протоколом. Источник кодируется строкой `jsqdb://recording/<id>` и
хранится в той же `FolderSpec`, что и пути к папкам.

```
LoadWorkspaceDataUseCase.Execute
   ├── *.xlsx              → ExportedProtocolDataSourceReader   (существует)
   ├── jsqdb://recording/  → PostgresRecordingDataSourceReader  (новое)
   └── папка               → ProvaMetadataReader + CanaliDefinitionReader
                             + DbfTestDataSourceReader           (существует)
```

Выбор такого представления даёт без дополнительной работы: смешение файловых и
«базовых» источников в одной рабочей области (до шести), слияние с разделением
совпадающих кодов, кнопку «Обновить», список недавних источников, сохранение
раскладок и пресетов. Вся эта машинерия уже опирается на строку источника.

Доступ к базе — исключительно на чтение. Ни одного `INSERT`, `UPDATE` или
`DELETE`: сервис-владелец базы остаётся единственным писателем.

### Новые компоненты

| Слой | Компонент | Назначение |
| --- | --- | --- |
| `Application/Database/` | `RecordingSourceRef` | Разбор и сборка строки `jsqdb://recording/<id>`; распознавание типа источника |
| `Application/Database/` | `DatabaseConnectionSettings` | Хост, порт, база, пользователь, пароль, интервал автообновления, таймауты |
| `Application/Database/` | `RecordingSummaryItem` | Строка списка прогонов: id, пост, название, статус, начало, длительность, модель, тип испытания |
| `Application/Workspace/Ports/` | `IRecordingCatalog` | Получение списка прогонов и статуса одного прогона |
| `Application/Workspace/Ports/` | `IRecordingDataReader` | Чтение рядов прогона, в том числе только хвоста после заданного момента |
| `Infrastructure/Database/` | `NpgsqlConnectionFactory` | Единственное место, знающее про Npgsql; строит строку подключения из настроек |
| `Infrastructure/Database/` | `PostgresRecordingCatalog` | Реализация `IRecordingCatalog` |
| `Infrastructure/Database/` | `PostgresRecordingDataSourceReader` | Реализация `ITestDataSourceReader` и `IRecordingDataReader` |
| `Infrastructure/Database/` | `RecordingRowsToTestDataMapper` | Разворот «длинного» результата в `TestData`; чистая функция, без обращений к сети |
| `Settings/` | `DatabaseSettingsRepository` | Чтение и запись настроек подключения, шифрование пароля DPAPI |
| `UI/` | `OpenFromDatabaseForm` | Диалог выбора прогонов |
| `UI/` | вкладка «База данных» в `SettingsDialog` | Редактирование параметров подключения |

Граница проведена так, что Npgsql виден только внутри
`Infrastructure/Database/`. Прикладной слой работает с портами
`IRecordingCatalog` и `IRecordingDataReader`, поэтому тестируется без сети.

## Чтение данных

Загрузка одного прогона — три запроса.

**Карточка прогона** заполняет `TestData.Meta`, откуда её берёт существующая
форма сведений о записи:

```sql
SELECT r.*, p.name AS post_name
FROM recordings r
JOIN posts p ON p.id = r.post_id
WHERE r.id = @id;
```

**Каналы** заполняют `TestData.Channels`. `channel_config.alias` становится
именем канала, `unit` — единицей; скрытые каналы пропускаются. Порядок берётся
из `channel_order.channel_ids` для соответствующего поста:

```sql
SELECT channel_id, alias, unit
FROM channel_config
WHERE post_id = @post AND NOT is_hidden;
```

**Ряды** заполняют `TestData.TimestampsMs` и `TestData.Columns`:

```sql
SELECT a.channel_id, a.window_start, a.avg_value
FROM recording_aggregates a
WHERE a.recording_id = @id
  AND a.window_start > @since
  AND NOT EXISTS (
        SELECT 1 FROM recording_aggregate_exclusions e
        WHERE e.recording_id = a.recording_id
          AND e.channel_id   = a.channel_id
          AND e.window_start = a.window_start
          AND e.restored_at IS NULL)
ORDER BY a.window_start;
```

При полной загрузке `@since` равен `-infinity`, при дозагрузке — последнему уже
загруженному `window_start`.

`RecordingRowsToTestDataMapper` разворачивает результат в «широкую» таблицу:
уникальные значения `window_start` в порядке возрастания становятся
`TimestampsMs`, значения раскладываются по `Columns[код]`. Окно, для которого у
канала нет строки — потому что оно исключено оператором или измерение не
пришло, — остаётся `null`, то есть разрывом на графике, а не смещением ряда.

`window_start` имеет тип `timestamptz`; в `TimestampsMs` кладётся Unix-время в
миллисекундах UTC. Это тот же формат, что `Core/DbfReader.cs` строит для
файловых источников, поэтому слияние источников разных типов корректно.

Префикс поста срезается по правилу «`<id поста>-` в начале кода»: `B-T1` → `T1`,
`C-MaxI` → `MaxI`. Пост при этом виден в имени источника
(`Post B · 2026-08-05 19:54`). Если в одну рабочую область загружены два поста,
совпавшие коды разводит существующий механизм разделения пересекающихся кодов
в `MergeLoadedSourcesUseCase`.

Загрузка выполняется в фоне с индикатором прогресса — так же, как сейчас
загружаются папки.

## Живое обновление

Если у загруженного прогона `status = 'recording'`, для него включается таймер с
интервалом из настроек (по умолчанию 30 с). На каждом тике:

1. Выполняется запрос рядов с `@since` = последний загруженный `window_start`.
2. Новые окна дописываются в хвост `TestData`, графики продлеваются.
3. Если новых окон нет, перерисовки не происходит.
4. Одновременно проверяется `recordings.status`; при переходе в `stopped`
   таймер останавливается сам.

Дозагружается только хвост, поэтому стоимость тика не зависит от длины прогона.

Сбой тика (сеть недоступна, база не отвечает) не показывает модальных окон:
источник помечается как «нет связи» в статусной строке, таймер продолжает
попытки, запись об ошибке уходит в лог. При восстановлении связи пометка
снимается.

Файловые источники в той же рабочей области таймер не затрагивает — они
обновляются существующей кнопкой «Обновить».

## Интерфейс пользователя

**Открытие.** Кнопка «Открыть из БД…» рядом с существующим выбором папки.
Открывает `OpenFromDatabaseForm` — таблицу прогонов со столбцами: дата начала,
пост, название, модель оборудования, тип испытания, длительность, статус.
Фильтры: пост, диапазон дат, тип испытания, подстрока названия. Допускается
выбор нескольких прогонов — суммарно с уже загруженными источниками не более
шести. Идущий прогон выделяется в списке.

**Настройки.** Вкладка «База данных» в `SettingsDialog`: хост, порт, база,
пользователь, пароль, интервал автообновления, кнопка «Проверить подключение»,
показывающая результат немедленно. Поля предзаполнены значениями
`192.168.66.100`, `5432`, `jsq_db`, `jsq_user`.

Пароль шифруется через `ProtectedData` (DPAPI, scope `CurrentUser`) и хранится в
том же JSON-файле настроек, что и остальные параметры. В открытом виде на диск
не попадает и в репозиторий не коммитится.

## Зависимость Npgsql

Проект — старого формата csproj под .NET Framework 4.8, сейчас без единого
NuGet-пакета. Npgsql добавляется через `packages.config` и `Reference` с
`HintPath`. DLL кладутся в репозиторий, чтобы сборка оставалась независимой от
сети, и добавляются в список файлов `installer/JSQViewer.iss`.

Нужна последняя версия Npgsql с таргетом `netstandard2.0` — версия 8, лежащая в
локальном кэше NuGet, собрана под `net8.0` и на 4.8 не встанет. Конкретная
версия и полный список транзитивных зависимостей (`System.Memory`,
`System.Threading.Tasks.Extensions`, `System.Runtime.CompilerServices.Unsafe`,
`Microsoft.Bcl.AsyncInterfaces`) определяются первым шагом реализации:
подобрать версию, собрать, убедиться, что подключение к живой базе работает.
До этого момента остальные шаги не начинаются.

## Обработка ошибок

| Ситуация | Поведение |
| --- | --- |
| База недоступна при открытии диалога | Сообщение с текстом ошибки и предложением проверить настройки; диалог не открывается |
| Неверные учётные данные | Отдельное сообщение «Не удалось пройти проверку подлинности», ссылка на настройки |
| Прогон удалён или недоступен | Источник не загружается, остальные источники рабочей области сохраняются |
| Сбой во время дозагрузки | Пометка «нет связи», запись в лог, повтор на следующем тике; загруженные данные остаются |
| Прогон без данных | Источник загружается пустым с предупреждением |

Таймаут подключения — 10 с, таймаут запроса — 120 с.

## Тестирование

Юнит-тесты в `JSQViewer.Tests`, все без обращения к сети:

- разбор и сборка строки `jsqdb://recording/<id>`, включая некорректные значения;
- срезание префикса поста, в том числе коды без префикса и коды с дефисом внутри
  (`T-avg`);
- разворот «длинного» результата в `TestData`: полный набор окон, пропуски от
  исключений, каналы с разным числом окон;
- дозагрузка хвоста: новые окна дописываются, уже загруженные не дублируются;
- ветвление `LoadWorkspaceDataUseCase` по типу источника;
- слияние источника из БД с файловым источником.

Порты `IRecordingCatalog` и `IRecordingDataReader` в тестах подменяются
заглушками.

Проверка на живой базе выполняется вручную по чек-листу, который добавляется в
`doc/`: открытие исторического прогона, сверка графика с веб-сервисом,
наблюдение за идущим прогоном не менее трёх тиков, разрыв связи и
восстановление, смешанная рабочая область из прогона БД и папки, экспорт в
шаблон.

## Вне объёма работ

Сознательно не делается в рамках этой задачи:

- чтение `recording_events` (события порогов и обрывов связи);
- чтение `recording_summaries`, `sessions`, `session_aggregates`,
  `ambient_aggregates`;
- загрузка расчётных каналов из `recording_computed_aggregates`;
- авторизация пользователей через таблицы схемы `auth` — подключение идёт под
  одной технической учётной записью;
- любая запись в базу.
