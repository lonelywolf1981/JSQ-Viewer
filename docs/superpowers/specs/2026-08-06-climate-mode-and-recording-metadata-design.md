# Климатический режим и метаданные прогона — дизайн

Дата: 2026-08-06
Статус: утверждён пользователем

## Задача

1. В таблице выбора прогонов из БД показывать климатический режим прогона — один из трёх: `25/60`, `32/65`, `40/40`.
2. После открытия прогона показывать в заголовке рабочего пространства модель оборудования, вид испытания и климатический режим — вдобавок к названию прогона.
3. Попутно устранить причину, по которой каналы `T-sie` и `UR-sie` не доходят до вьюера.

Модель и вид испытания в таблице выбора уже реализованы (`UI/OpenFromDatabaseForm.cs:300-301`), заполнены в 191 прогоне из 193 и в этой работе не меняются.

## Исходные данные

Проверено на рабочей базе (192.168.66.100/jsq_db, чтение):

- Справочник `climate_modes` содержит ровно три строки: `25_60` (25 °C / 60 %), `32_65` (32 / 65), `40_40` (40 / 40).
- Колонка `recordings.climate_mode` заполнена у 5 прогонов из 193.
- Каналы `T-sie` («Температура камеры») и `UR-sie` («Влажность камеры») заданы в `channel_config` с `post_id = 'common'` и `is_common = true`. В `recording_aggregates` они присутствуют у всех проверенных прогонов.
- Первое окно `T-sie` даёт чёткие кластеры: 25.1–25.2 и 32.0–32.6. Влажность `UR-sie` у прогонов режима 32/65 разбросана 55.1–65.6 и для классификации непригодна.

## Решение

### 1. `ClimateModeResolver` — определение режима

Новый класс в `Application/Database/`. Без SQL, без WinForms, тестируется напрямую.

Известные режимы заданы константами: 25, 32, 40 °C с метками `25/60`, `32/65`, `40/40`. Метка получается из идентификатора БД заменой `_` на `/`, поэтому справочник `climate_modes` дополнительно не читается.

Порядок определения:

1. Если `recordings.climate_mode` непустое и соответствует одному из трёх идентификаторов — берём его, источник `FromRecord`.
2. Иначе берём среднее `avg_value` канала `T-sie` по первым пяти окнам и выбираем ближайший режим по температуре. Если отклонение больше **3 °C** — режим не определён.
3. Если `T-sie` у прогона нет — режим не определён.

Неопределённый режим означает пустую ячейку в таблице и отсутствие поля в заголовке. Никакой заглушки вроде «неизвестно» не выводим.

Влажность в классификации не участвует. `UR-sie` читается только для подсказки.

Результат — тип `ClimateModeInfo` с полями `Label` (например `32/65`), `Source` (`FromRecord` / `FromChannels` / `Unknown`), `TemperatureCelsius` и `HumidityPercent` (nullable, для подсказки).

### 2. Каталог прогонов

`RecordingCatalogQueryBuilder` оборачивает текущий запрос в CTE и добавляет два коррелированных подзапроса:

```sql
WITH page AS (
  SELECT r.id, r.post_id, r.title, r.status, r.started_at, r.stopped_at,
         r.equipment_model, r.experiment_type, r.climate_mode
  FROM recordings r
  WHERE <существующие условия>
  ORDER BY r.started_at DESC NULLS LAST
  LIMIT @limit)
SELECT p.*,
  (SELECT avg(t.v) FROM (
     SELECT a.avg_value v FROM recording_aggregates a
     WHERE a.recording_id = p.id AND a.channel_id = 'T-sie' AND a.avg_value IS NOT NULL
     ORDER BY a.window_start LIMIT 5) t) AS t_avg,
  (SELECT avg(u.v) FROM (
     SELECT a.avg_value v FROM recording_aggregates a
     WHERE a.recording_id = p.id AND a.channel_id = 'UR-sie' AND a.avg_value IS NOT NULL
     ORDER BY a.window_start LIMIT 5) u) AS ur_avg
FROM page p
ORDER BY p.started_at DESC NULLS LAST
```

Существующие фильтры (пост, даты, тип испытания, подстрока названия) и порядок параметров сохраняются — меняется только обёртка. Внутренний `ORDER BY` в CTE нужен только для того, чтобы `LIMIT` отобрал правильную страницу; PostgreSQL не гарантирует, что этот порядок переживёт внешний `SELECT`, поэтому внешний запрос сортирует ещё раз — по уже отобранным ≤500 строкам это бесплатно.

Форма запроса важна, все три варианта замерены на рабочей базе (193 прогона, 500 в лимите):

| Вариант | Время |
|---|---|
| `ORDER BY window_start LIMIT 5` в подзапросе, `LIMIT` до соединения | **48 мс** |
| `row_number() OVER (PARTITION BY channel_id …)` внутри LATERAL | 10 000 мс |
| То же без CTE, соединение до `LIMIT` | 11 672 мс |

Оконная функция заставляет прочитать все окна канала целиком, поэтому применяется только связка `ORDER BY window_start LIMIT 5`: она идёт по префиксу первичного ключа `(recording_id, channel_id, window_start)`. Отступать от этой формы при реализации нельзя.

`RecordingSummaryItem` получает свойство `ClimateMode` типа `ClimateModeInfo`. Заполняет его `PostgresRecordingCatalog`, вызывая резолвер.

### 3. Таблица выбора прогонов

В `OpenFromDatabaseForm` добавляется колонка «Режим» шириной 80 после «Вид испытания». Значение — `ClimateMode.Label`, пусто при неопределённом режиме.

Подсказка на ячейке:

- источник `FromRecord` — «Из карточки прогона»;
- источник `FromChannels` — «Определён по T-sie: 32.3 °C, UR-sie: 64.1 %».

Отдельного маркера вычисленного значения (вроде `≈`) не вводим: источник виден в подсказке.

### 4. Заголовок рабочего пространства

`PostgresRecordingDataSourceReader` добавляет в `TestData.Meta` ключ «Климатический режим». Резолвер вызывается тем же способом, что и в каталоге; для одного прогона запрос занимает 1 мс. Ключи «Модель оборудования» и «Тип испытания» в `Meta` уже есть.

Состав имени собирает `RecordingDisplayNameBuilder` в момент чтения прогона — это **отображаемое имя источника**, а не только заголовок окна графика:

```
Post B 2026-08-06 14-33-12 · LIDER · NPT14RA · FUNC · 32/65
```

Порядок частей повторяет принятую в лаборатории схему именования папок (`04.08.2026 REX NUY45 65G POWER`): название, модель, компрессор, вид испытания, климатический режим. Пустые части выпадают вместе с разделителем. Из марки компрессора отбрасывается суффикс напряжения и частоты (`NPT14RA (220-240V/50Hz)` → `NPT14RA`) — полное значение остаётся в карточке метаданных.

Поскольку данные попадают в само имя, они видны везде, где показывается имя источника: заголовок окна графика, окно каналов («Каналы: …»), окно источника, легенда сравнения. `WorkspaceTitleBuilder` ничего не дописывает — он по-прежнему просто перечисляет имена через `; ` при нескольких источниках. Для папочных источников (DBF) этих ключей в `Meta` нет, имя остаётся именем папки.

Расширенный заголовок применяется там, где рабочее пространство уже показывает название: окно графика и открепляемые окна графиков (`MainForm.BuildChartWindowCaption`). Заголовок главного окна остаётся «JSQ Viewer <версия>» — он не менялся при загрузке и раньше.

Расширение заголовка включается по факту наличия в `Meta` ключей «Модель оборудования», «Тип испытания» и «Климатический режим» (см. `WorkspaceMetadataKeys`), а не по типу источника — поэтому загрузчики папочных источников (DBF и любые будущие не-БД загрузчики) не должны писать эти ключи в `Meta`. Сегодня их пишет только `PostgresRecordingDataSourceReader`; это инвариант, а не совпадение. При объединении нескольких прогонов (`MergeLoadedSourcesUseCase`) все три ключа удаляются из объединённых метаданных, потому что `Meta` рабочего пространства общий на всё пространство и не может быть достоверно привязан к одному из объединённых источников.

### 5. Общие каналы `T-sie` и `UR-sie`

`PostgresRecordingDataSourceReader` фильтрует конфигурацию каналов по `cc.post_id = r.post_id` (`ChannelsSql`, строка 39; `RowsSql`, строка 53). Каналы с `post_id = 'common'` под это условие не попадают и молча отбрасываются, хотя данные по ним в агрегатах есть.

Условие в обоих запросах меняется на `(cc.post_id = @post OR cc.is_common)` и `(cc.post_id = r.post_id OR cc.is_common)` соответственно. После этого температура и влажность камеры отображаются как обычные каналы, и определённый режим можно проверить глазами на графике.

Существующая логика скрытых каналов (`NOT cc.is_hidden`) и исключённых точек не затрагивается.

## Тестирование

Разработка по TDD, красный→зелёный на каждом шаге.

- `ClimateModeResolver`: каждый из трёх режимов по температуре; граница допуска (ровно 3 °C — определён, 3.1 °C — нет); приоритет `recordings.climate_mode` над вычислением; неизвестный идентификатор в колонке БД; отсутствие данных `T-sie`; усреднение по пяти окнам при менее чем пяти доступных.
- `RecordingCatalogQueryBuilder`: наличие CTE и бокового соединения; сохранение всех существующих фильтров и имён параметров; неизменный порядок сортировки.
- `WorkspaceTitleBuilder`: один источник со всеми полями; один источник с пропусками; один источник без метаданных (папка); несколько источников — поведение не изменилось.
- Маппер метаданных: ключ «Климатический режим» появляется в `Meta`.
- Регрессия: полный прогон набора тестов, сборки Debug и Release без ошибок и предупреждений.

Запросы к БД в автотестах не выполняются — резолвер и построитель запроса тестируются на данных в памяти и на тексте SQL. Проверка на живой базе выполняется вручную по чек-листу.
